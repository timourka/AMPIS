# План выполнения лабораторной работы № 2

## Основание и границы работы

Источник требований: `Задание ПИ 2.pdf`, разделы «Основные функциональный возможности», «Требования по реализации», «Логическая схема», «Интеграция» и «Сценарии для проверки задания».

Нужно реализовать многопользовательский файловый сервис: регистрация и вход, загрузка файлов размером не более 1 Мб, скачивание, удаление, изменение имени пользователя, статистика, поиск, сортировка и пагинация.

План рассчитан на реализацию всех 12 функциональных пунктов. Цветовая градация оценок в извлечённом тексте PDF не сохранилась, поэтому распределение пунктов по оценкам здесь не утверждается.

Из первой работы не переносим конвертацию в PDF, лимит 128 Мб, CDN и другие требования из статьи: во втором задании они не указаны.

## 1. Зафиксировать архитектурные решения

- [ ] Использовать компоненты из задания: G1 – шлюз, S1 – пользователи и авторизация, S2 – загрузка и удаление, S3 – скачивание и история скачиваний, S4 – списки, поиск и отчёты, D1 – шина событий.
- [ ] Выбрать стек. Предлагаемый вариант: ASP.NET Core, PostgreSQL, RabbitMQ и Docker Compose. Это рекомендация, а не требование задания.
- [ ] Отдельно определить хранение файлов. В задании показано общее B2 для S2 и S3, но одновременно требуется своя БД у каждого сервиса. Не подключать S2 и S3 к одной общей БД без согласования.
- [ ] Предлагаемый вариант для лабораторной: S2 хранит исходные файлы и метаданные в своей БД; S3 хранит собственную копию файла и историю скачиваний в своей БД. S3 получает файл через событие S2. Для небольших файлов содержимое можно передавать в сообщении; проверить ограничения брокера с учётом накладных расходов кодирования. S4 получает метаданные и строит свои списки и отчёты.
- [ ] Отдельные БД могут работать в одном экземпляре PostgreSQL, но сервис не должен читать таблицы другого сервиса. Для каждого сервиса создать свою учётную запись с доступом только к своей БД.
- [ ] Зафиксировать допущения: удалять файл и смотреть подробную статистику может его владелец; анонимные скачивания учитываются без имени; файлы и изменения становятся видны после доставки событий. Ограничение удаления владельцем – предлагаемое правило доступа, в тексте задания оно явно не определено.
- [ ] Зафиксировать точный лимит файла в байтах: «1 Мб» в задании не уточнён. Принятое значение использовать одинаково в шлюзе, сервисе и тестах.

Результат: схема компонентов, таблица ответственности и список согласованных допущений.

## 2. Описать API, данные и события

### HTTP API через G1

- Регистрация и вход – S1.
- Изменение собственного имени – S1.
- Загрузка и удаление файла – S2.
- Скачивание файла – S3.
- Список файлов с поиском, сортировкой и пагинацией – S4.
- Статистика собственного файла – S4.

Конкретные URL и форматы запросов закрепить перед реализацией. Все пользовательские запросы проходят через шлюз; сервисные HTTP-порты не публикуются наружу.

### Данные

- S1: пользователи, хеши паролей, профили, исходящие события.
- S2: файлы, владельцы, имена, размеры, содержимое, состояние удаления, исходящие события.
- S3: копии файлов, локальные сведения о пользователях при необходимости, история скачиваний, исходящие события и обработанные входящие события.
- S4: пользователи, карточки файлов, счётчики и история скачиваний для отчётов, обработанные события.

### События

- `UserRegistered`, `UserProfileChanged`.
- `FileUploaded`, `FileDeleted`.
- `FileDownloaded`.

Для события определить `eventId`, тип, версию схемы, время, идентификатор сущности, версию сущности при необходимости и полезные данные. Владельца связывать с файлом по неизменному `userId`, а не по имени.

Результат: описание API и схемы событий с примерами, правила обработки повторов и порядка событий.

## 3. Подготовить окружение

- [ ] Создать проекты шлюза и четырёх сервисов.
- [ ] Описать Docker Compose: G1, S1–S4, RabbitMQ, отдельные БД и постоянные тома.
- [ ] Добавить миграции БД, конфигурацию через переменные окружения и проверки состояния.
- [ ] Разделить очереди подписчиков: S3 и S4 должны получать собственные копии нужных событий, а не конкурировать за одну очередь.
- [ ] Настроить постоянные очереди и сообщения, подтверждения публикации и ручное подтверждение обработки сообщений.

Результат: окружение запускается одной командой; данные сохраняются после перезапуска контейнеров.

## 4. Реализовать S1 и проверку доступа

- [ ] Регистрация с уникальным логином и безопасным хешированием пароля.
- [ ] Вход и выдача JWT.
- [ ] Изменение собственного имени и публикация событий профиля.
- [ ] Локальная проверка подписи JWT без обращения к S1 при каждом запросе. Проверять также срок действия, издателя и получателя токена.
- [ ] Не доверять присланным клиентом заголовкам с идентификатором пользователя.
- [ ] Гостевые запросы к S3 и S4 не должны зависеть от доступности S1.

Проверка: регистрация, корректный и неверный пароль, повторный логин, истёкший токен, изменение имени, доступ гостя при остановленном S1.

## 5. Реализовать загрузку, доставку файла и скачивание

- [ ] S2 принимает файл только от авторизованного пользователя.
- [ ] Проверяет фактический размер при чтении потока, а не только заголовок запроса.
- [ ] Сохраняет файл под внутренним идентификатором; исходное имя использует только как метаданные.
- [ ] Файл и запись исходящего события фиксируются одной транзакцией в БД S2.
- [ ] S3 получает событие и сохраняет собственную копию файла без доступа к БД S2.
- [ ] S4 получает событие и создаёт карточку файла.
- [ ] S3 отдаёт исходное содержимое с корректным именем и безопасным `Content-Disposition`.
- [ ] При скачивании S3 сохраняет запись истории и событие `FileDownloaded`; S4 обновляет счётчик и отчёт.
- [ ] Определить, что считается скачиванием. Факт получения всех байтов клиентом сервер гарантировать не может; для лабораторной явно описать принятую точку учёта успешной выдачи.

Проверка: полный путь «загрузка → появление в списке → скачивание → обновление счётчика», совпадение содержимого файлов, граничные размеры, анонимное и авторизованное скачивание.

## 6. Реализовать удаление и изменение отображаемых данных

- [ ] S2 проверяет право удаления и фиксирует удаление вместе с исходящим событием.
- [ ] S3 по событию прекращает выдачу файла, S4 убирает файл из списка.
- [ ] Повторное получение события удаления не вызывает ошибку и не восстанавливает файл.
- [ ] Предусмотреть защиту от запоздавшего события загрузки после удаления: версия сущности или сохранённая отметка удаления.
- [ ] После изменения имени S4 обновляет имя владельца и имена пользователей в статистике, сохраняя связи по `userId`.

Проверка: удаление своего и чужого файла, повторное удаление, скачивание после обработки удаления, смена имени владельца и скачавшего пользователя.

## 7. Реализовать S4 полностью

- [ ] Публичный список: ссылка, имя файла, имя владельца, количество скачиваний.
- [ ] Поиск по названию файла и имени владельца.
- [ ] Сортировка по имени файла, имени владельца и количеству скачиваний.
- [ ] Пагинация с проверкой параметров и стабильным дополнительным порядком по идентификатору.
- [ ] Отчёт владельцу: количество скачиваний и имена скачавших пользователей; анонимные скачивания отмечаются отдельно.
- [ ] Данные для ответов берутся только из БД S4, без синхронных запросов к S1–S3.

Проверка: пустой список, отсутствие результатов, одинаковые имена, границы страниц, все поля сортировки, запрет чужого отчёта и обновление данных после событий.

## 8. Обеспечить восстановление после сбоев

- [ ] Использовать transactional outbox в сервисах, которые меняют данные и публикуют события: событие сначала сохраняется в той же транзакции, что и изменение, затем доставляется брокеру.
- [ ] Подтверждать входящее сообщение только после успешной транзакции БД получателя.
- [ ] Дедуплицировать события по `eventId`, особенно для счётчиков скачиваний.
- [ ] Настроить повторную доставку, обработку ошибок и очередь необработанных сообщений.
- [ ] Для временного отключения D1S4 останавливать потребителя или соединение, не удаляя очередь и подписку.
- [ ] На шлюзе задать тайм-ауты: недоступность одного сервиса даёт ошибку только его маршрутам.
- [ ] Добавить логи с идентификатором запроса и события, без паролей и токенов.

Результат: после восстановления соединения накопленные события обрабатываются автоматически, данные не теряются и счётчики не увеличиваются повторно.

## 9. Выполнить обязательные сценарии из задания

| Сценарий | Ожидаемое поведение |
|---|---|
| Остановить S2 | S1, S3 и S4 продолжают работать; ранее доставленные файлы скачиваются |
| Остановить S3 | S1, S2 и S4 работают; скачивание недоступно, остальные функции доступны |
| Остановить S4 | S1, S2 и S3 работают; списки и отчёты недоступны |
| Остановить S1 | Гостевой список и скачивание доступны без регистрации |
| Отключить D1S4 | S4 показывает последнее полученное состояние; остальные сервисы продолжают работать |
| Восстановить D1S4 | Списки и статистика автоматически догоняют изменения |

Дополнительные проверки: повтор одного события, перезапуск потребителя до подтверждения сообщения, временная недоступность брокера, смена имени во время отключения S4, удаление во время отключения S4.

Результаты зафиксировать: действия, ожидаемое поведение, фактическое поведение, логи или снимки экрана. Эти проверки в рамках составления плана ещё не выполнялись.

1. Архитектура, допущения, API и события.
2. Окружение и каркасы сервисов.
3. Регистрация, вход и проверка доступа.
